Кейс-портфолио: Проектирование ПО «ЛекарстваTime»
Сфера проекта: HealthTech (Здравоохранение, Фармация).
Роль: Единственный системный аналитик на проекте.
Задача: Спроектировать архитектуру, интеграции и бизнес-логику кроссплатформенного приложения для контроля приема медикаментов и интеграции с аптечными сетями.

1. Сбор и анализ требований
Начальным этапом проекта стало выявление потребностей бизнеса и пользователей.
  Проведенные активности: Интервьюирование Product Owner и эксперта предметной области (ведущего провизора).
  Результат: Сформированы бизнес-требования (BRD). Выявлены ключевые законодательные ограничения, в частности необходимость строгого соблюдения 152-ФЗ «О персональных данных» при обработке медицинской информации пользователей.

2. Разработка спецификации требований к ПО (SRS)
На основе собранных данных была разработана и согласована сквозная спецификация требований (версия 1.0).
  Функциональные требования (FR): Описана логика управления карточками лекарств, учет остатков упаковок, логика push-уведомлений и интеграция со сторонними сервисами справочников аптек.
  Нефункциональные требования (NFR): Зафиксированы метрики производительности системы:
    Целевая нагрузка: до 1000 RPS (запросов в секунду).
    Время отклика (Latency): не более 500 мс для 95% запросов.
  
3. Моделирование бизнес-процессов и Use Cases
Для формализации логики взаимодействия пользователей с системой были созданы визуальные модели в PlantUML:
  Use Case моделирование: Разработана общая диаграмма прецедентов и детально специфицировано 7 основных пользовательских сценариев (включая регистрацию, добавление медикаментозных карт, обработку приемов и сценарий удаления аккаунта согласно праву «на забвение»).
  Бизнес-логика бэкенда: Прописан пошаговый алгоритм автоматического пересчета остатков препарата при отметке приема и отправка триггерных push-уведомлений, если количество таблеток падает ниже 10% от объема упаковки.

4. Проектирование модели данных (ERD)
Разработана концептуальная диаграмма классов и логическая модель базы данных (PostgreSQL):
  Спроектирована связь «один-ко многим» (1:M) между сущностями пользователей (User), карточками лекарств (MedicationCard) и записями приемов (IntakeRecord).
  Архитектурное решение: В соответствии с требованиями безопасности, вложения-рецепты (Attachment) привязаны к локальному хранилищу конкретного мобильного устройства, разгружая центральную БД и минимизируя риски утечки чувствительных файлов.

5. Проектирование контрактов API (OpenAPI 3.0)
Разработана полноценная спецификация интеграционного взаимодействия для фронтенда и внешних систем.
  Формат контрактов: OpenAPI 3.0 (YAML/Swagger).
  Реализованная логика:
    Описана авторизация по протоколу JWT (Bearer Auth).
    Разработана структура эндпоинтов, query-параметров и объектов ответов для синхронизации медицинских карт.
    Проектирование ответов на ошибки с валидными HTTP-статусами (400 Bad Request, 0.1.2, 404 Not Found) и кастомными телами ошибок для фронтенда.
